# Contributing to ViewerHub

Thank you for your interest in improving ViewerHub! This document explains how to report issues and submit changes so they can be handled efficiently.

ViewerHub manages medical-imaging viewers (Weasis, OHIF, 3D Slicer...) across an IT infrastructure. For user and administrator documentation, see the [ViewerHub documentation](https://weasis.org/en/viewer-hub/index.html). Local setup (Docker services, Keycloak, Minio, PACS, run configuration) is described in the [README](README.md).

By participating in this project you agree to abide by our [Code of Conduct](.github/CODE_OF_CONDUCT.md). Security issues must be reported privately, following the [Security Policy](.github/SECURITY.md) — never in a public issue, discussion, or pull request.

## Reporting issues

Before opening an issue:

1. **Search first** — check [existing issues](https://github.com/nroduit/viewer-hub/issues), [documentation](https://weasis.org/en/viewer-hub) and [Discussions](https://github.com/nroduit/viewer-hub/discussions). Duplicates will be closed.
2. **Provide the information needed to reproduce.** A useful bug report includes:
   - the ViewerHub version (or commit) and how it is deployed (Docker image, local run, Kubernetes),
   - the relevant configuration: active Spring profiles, connector type (`connectors-dicom-no-gtw`, `connectors-dicom-gtw`, `connectors-dicomweb-gtw`), archive (dcm4chee, Orthanc, …), viewer being launched, and whether the [gateway](https://github.com/nroduit/viewer-hub-gateway) is in use,
   - the launch URL or admin UI action that triggers the problem, with identifiers anonymized,
   - clear steps to reproduce, what you expected versus what actually happened,
   - relevant application logs and, when applicable, a screenshot.
3. **Ask questions in [Discussions](https://github.com/nroduit/viewer-hub/discussions)**, not in the issue tracker. Issues are for actionable bug reports and well-defined enhancement requests.
4. **Never post patient data.** Manifests, logs, screenshots, and DICOM attachments must be synthetic or fully anonymized (see the [Code of Conduct](.github/CODE_OF_CONDUCT.md)).

Issues that cannot be reproduced or acted upon with the information provided may be closed with a reference to this document. You are welcome to reopen the discussion once the missing details are available.

## Submitting pull requests

1. **Discuss significant changes first.** For anything beyond a small fix, open an issue or a [discussion](https://github.com/nroduit/viewer-hub/discussions) before investing time, so the approach can be aligned with the maintainers.
2. **Keep pull requests focused.** One logical change per PR. Avoid mixing refactoring, formatting, and functional changes.
3. **Follow the project conventions.**
   - Build with JDK 25 and Maven; the Vaadin frontend build needs Node 24 and pnpm.
   - Make sure the build used by CI passes: `mvn -Punit-test,coverage -B verify` (the `unit-test` profile skips the Vaadin frontend build; integration tests need the Docker infrastructure described in the README and are not run in CI).
   - Keep the EPL-2.0 OR Apache-2.0 license header on every source file, and match the formatting and naming of the surrounding code.
4. **Explain the motivation.** The PR description must state what problem is being solved and why this approach was chosen — not just restate the diff.
5. **Test your change.** Describe how it was verified (unit tests, manual testing against which archive, viewer, and profile). Untested changes will not be merged.
6. **Be careful with security-sensitive areas.** Changes touching authentication, OAuth2 token handling, URL cryptography, manifest generation, or access control receive extra scrutiny; explain the security impact explicitly.

## AI-assisted and AI-generated contributions

AI tools (Claude, ChatGPT, Copilot, etc.) are welcome as an *assistant* — but **you**, the human contributor, are the author and remain fully responsible for everything you submit.

Requirements for any AI-assisted issue or pull request:

- **Understand what you submit.** You must be able to explain the problem, the change, and answer review questions yourself. "The AI wrote it" is not an acceptable answer during review.
- **Verify before submitting.** Reproduce the bug yourself before reporting it; build, run, and test the code yourself before opening a PR. AI output frequently references APIs, endpoints, properties, or behaviors that do not exist in ViewerHub.
- **Be transparent.** If a substantial part of an issue or PR was generated by an AI tool, say so in the description.
- **No unsolicited bulk submissions.** Mass-generated issues, speculative "findings" (e.g., unverified security or bug reports produced by scanning tools or LLMs), and large machine-generated refactorings are not accepted.

Maintainer time is the scarcest resource in this project. Issues and pull requests that show signs of unreviewed AI generation — vague or generic descriptions, code that does not compile or does not match the codebase, fabricated references, boilerplate padding, or missing information — **may be closed without detailed review, citing this section**. This is not a judgment of the contributor; it simply keeps the tracker usable. You are welcome to resubmit after verifying and completing the content yourself.
